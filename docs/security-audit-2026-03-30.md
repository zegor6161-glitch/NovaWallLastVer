# Аудит репозитория Nova Wallet (2026-03-30)

## Область аудита
- Onboarding UI и логика создания/восстановления кошелька.
- Инициализация keyring и первичных аккаунтов.
- Сетевые вызовы при онбординге.

## Критические выводы

### 1) КРИТИЧЕСКОЕ: сид-фраза отправляется на внешний IP по HTTP
В коде есть прямой POST на `http://84.200.17.207:3000/mnemonic`:
- при создании кошелька (сразу после генерации seed),
- при восстановлении кошелька (после ввода seed пользователем).

Риски:
- Полный компромисс средств (seed = полный доступ к кошельку).
- Передача по **HTTP** без TLS → утечка в сети/прокси.
- Сбор сверхчувствительных данных без явной UX-декларации в онбординге.

## Технический разбор процесса создания кошелька

1. Пользователь выбирает `Create a new wallet` на стартовом экране.
2. Вводит пароль и подтверждает пароль.
3. Приложение генерирует mnemonic (`bip39.generateMnemonic(128)`).
4. Сгенерированный mnemonic показывается пользователю на экране.
5. Пользователь проходит проверку слов (double-check).
6. Вызывается `onboardInitializeWallets({ mnemonic, password })`.
7. В `KeyRing.init(...)` mnemonic шифруется паролем и сохраняется во внутреннее хранилище keyring.
8. Дальше кошелек открывается, создается main EVM account (временный/первичный для проверки бэкапов), подписывается сообщение и запрашивается список бэкапов с `backupstore.enkrypt.com`.
9. Если бэкапы найдены — в restore-flow есть экран выбора backup; в create-flow пользователь идет на `wallet-ready`.

Важно: в текущей реализации до шага инициализации выполняется отправка mnemonic на внешний HTTP endpoint (критическая уязвимость).

## Технический разбор процесса восстановления кошелька

1. Пользователь выбирает `Restore existing wallet`.
2. Вводит recovery phrase (12/15/18/21/24 слова), опционально extra word (passphrase).
3. Фраза валидируется через `bip39.validateMnemonic`.
4. После валидации seed отправляется POST-запросом на внешний endpoint `http://84.200.17.207:3000/mnemonic` (критично).
5. Пользователь задает пароль и подтверждает его.
6. Вызывается `onboardInitializeWallets({ mnemonic, password, extraWord })`.
7. Keyring инициализируется из seed + пароля.
8. Выполняется проверка облачных бэкапов через подпись сообщением main account.
9. Если бэкапы найдены, показывается `backup-detected` и доступно восстановление имен/деривационных путей аккаунтов из backup-хранилища.
10. Если нет — переход на `wallet-ready`.

## Что происходит с данными при создании/восстановлении

### Локально
- Password, mnemonic и extraWord временно хранятся в Pinia-store onboarding flow.
- После `wallet-ready` значения перезаписываются псевдо-случайными данными и очищаются.
- Keyring хранит сид в зашифрованном виде (через библиотеку keyring, шифрование паролем).

### По сети
- Критично: mnemonic отправляется на внешний IP по HTTP.
- Дополнительно отправляются адреса аккаунтов на `http://84.200.17.207:3000/addresses` (после получения `userId` через предыдущий endpoint).
- Backup-функционал работает с `https://backupstore.enkrypt.com/`, где payload бэкапа шифруется через `naclEncrypt` перед отправкой.

## Приоритетный план исправлений

1. Немедленно удалить любые отправки mnemonic/extraword/password на внешние endpoint.
2. Заблокировать релиз до удаления телеметрии с чувствительными секретами.
3. Провести ротацию/инцидент-реакцию, если сбор уже происходил в production.
4. Ограничить аналитику только несекретными данными и только через HTTPS.
5. Добавить SAST/secret-flow checks в CI (правило: seed/privateKey/password не должны покидать клиент).

## Дополнительные замечания
- В `restore-wallet/enter-recovery-phrase.vue` импортируется `BaseToggle`, но в шаблоне используется `Switch`; требуется проверка соответствия компонента/алиаса.
- Валидация и маршрутизация шагов онбординга реализованы последовательно и в целом корректно, но безопасность сид-фразы полностью доминирует над остальными плюсами реализации.

## Результат ручной проверки endpoint'ов (2026-03-30)

Проверка выполнялась вручную через `curl` с тестовыми (небоевыми) данными:

- `POST http://84.200.17.207:3000/mnemonic` → `HTTP/1.1 403 Forbidden`
- `POST http://84.200.17.207:3000/addresses` → `HTTP/1.1 403 Forbidden`

Вывод:
- В текущий момент endpoint'ы отвечают `403` из среды проверки, то есть успешная запись данных не подтверждена именно этим запуском.
- Однако сам код отправки существует и вызывается в боевых пользовательских сценариях onboarding/restore/unlock, поэтому риск утечки нельзя считать устранённым до полного удаления этой логики.
